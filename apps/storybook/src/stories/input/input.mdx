## Accessibility contract — consumer owns the accessible name

Our one usage guideline for Input: **form controls must have an accessible name**, created with a `<label>` element or the `Field` component. Input supplies no labeling machinery of its own. A bare `<Input />` with no wrapping `<label>`, no `aria-label`, and no ambient `Field.Label` has **no accessible name**. This is the consumer half of the two-sided a11y contract: Base UI guarantees the ARIA/keyboard/focus wiring once you _do_ label it, but naming the control is on you.

- **Standalone labeling**: wrap in a plain `<label>` (the docs hero pattern), no extra props. Outside any `Field`/`Form` tree, `data-disabled` is the only state attribute that still means anything; there is no `data-touched`/`data-valid`/`data-dirty`, since there is no Field validity state machine to drive them.

- **Field-integrated labeling**: `aria-labelledby`/`htmlFor` auto-wired from `Field.Label`'s id, inherited unmodified from `Field.Control`.
- **Disabled cascade from an ancestor `Fieldset.Root`**: the native `disabled` attribute reaches an `Input` nested inside a `Field.Root` two levels down, without `Input` ever receiving `disabled` directly:

- **Known issue**: [#4643](https://github.com/mui/base-ui/issues/4643) ("How to clear the input value on a button click?") is open; we have no dedicated recipe in the docs yet. The standard controlled `value`/`onValueChange` triplet, reset externally, is the expected pattern.
