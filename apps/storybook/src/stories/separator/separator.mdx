A separator element accessible to screen readers.

- **Import:** `import { Separator } from '@base-ui/react/separator';`
- **Parts:** single-part, with no Root/parts namespace; used directly as `<Separator />`.
- **Status:** Stable. Shipped 2024-09-27 ([#535](https://github.com/mui/base-ui/pull/535)), originally generalized out of Menu's own grouping needs.
- **ARIA pattern:** none. There is no standalone "Separator" pattern in the W3C ARIA APG; guidance lives in the core [WAI-ARIA 1.2 role spec](https://www.w3.org/TR/wai-aria-1.2/#separator), which draws the widget-vs-document-structure distinction that our Separator sits on the document-structure side of.

<Canvas of={SeparatorStories.Hero} />

## Features

- **Accessibility-first purpose**: the component exists to be a separator element accessible to screen readers, so `role="separator"` and `aria-orientation` are applied unconditionally.
- **Orientation drives both ARIA and styling**: `orientation` sets `aria-orientation` directly and `data-orientation` automatically (via the generic state→data-attribute engine), so a single prop covers both concerns.
- **Reused across the library**: six compound components re-export the same `Separator` unchanged; one (`Toolbar`) wraps it with one added behavior (see below).
- **Minimal, stable surface**: only four props exist (`orientation`, `render`, `className`, `style`); fully stateless, no effects, no refs beyond the forwarded one.

## Anatomy

```tsx
import { Separator } from '@base-ui/react/separator';

<Separator />;
```

Renders a single `<div>` with no sub-parts and no required children. The consumer sizes/styles it (width/height via CSS) to read visually as a line.

**One component wraps rather than re-exports plainly: Toolbar.** `packages/react/src/toolbar/index.parts.ts` uses `export { ToolbarSeparator as Separator } from './separator/ToolbarSeparator';`. `ToolbarSeparator` renders the standalone `Separator` internally but **auto-inverts orientation** relative to the toolbar's own orientation (`{ vertical: 'horizontal', horizontal: 'vertical' }[context.orientation]`): a horizontal toolbar gets vertical dividers by default, and vice versa. The shared logic lives in the parent and flows through context rather than being reimplemented. The inversion is by design ([#4647](https://github.com/mui/base-ui/issues/4647)): a reporter assumed it was a bug affecting screen reader behavior, but we closed the issue as `type: expected behavior` because a horizontal toolbar's vertical dividing lines are visually and semantically correct.

## Choosing the right props

- **`orientation`**: use `'vertical'` when dividing horizontally-arranged content (inline nav links, horizontal toolbar groups); default `'horizontal'` for stacked content. We added it after the initial release ([#1303](https://github.com/mui/base-ui/issues/1303) / [#1304](https://github.com/mui/base-ui/pull/1304)) for parity with Radix UI, React Spectrum, Ariakit, Tamagui, and MUI's Divider.
- **`render`**: standard polymorphic-element escape hatch; swap the rendered `<div>` for another tag/component (e.g. `<hr />`).
- **`className` / `style`**: standard state-aware hooks; `state` here is just `{ orientation }`.
