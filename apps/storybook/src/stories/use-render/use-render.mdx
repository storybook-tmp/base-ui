# useRender

Hook for enabling a render prop in custom components.

- **Import:** `import { useRender } from '@base-ui/react/use-render';`
- **Shape:** a hook, not a component, and the only rendering primitive among Base UI's utils. It is `useRenderElement(defaultTagName, params, params)` under the hood, the same machinery every Base UI part uses.
- **Status:** Stable, public since [#1418](https://github.com/mui/base-ui/pull/1418).

## The blessed Slot alternative

Issue [#1315](https://github.com/mui/base-ui/issues/1315) asked for a Radix-`<Slot/>`-style helper so consumers could build their own render-prop-capable components. We discussed it as a team and decided that a **hook is a better abstraction than a `<Slot/>` component**. It shipped as `useRender` in [#1418](https://github.com/mui/base-ui/pull/1418), kept fully featured with `state` support, while `mergeProps` was split out as its own standalone primitive rather than bundled in.

The `render` prop itself is Base UI's permanent composition primitive. We declined a later `asChild` request ([#3983](https://github.com/mui/base-ui/issues/3983)) and are unlikely to change this API: `render` keeps composition explicit and avoids `cloneElement`. `useRender` is the supported way to extend that same convention into your own components, and the migration target for Radix `Slot`.

## Building a custom render-prop component

<Canvas of={UseRenderStories.CustomComponent} />

```tsx title="The Text component above"
interface TextProps extends useRender.ComponentProps<'p'> {}

function Text(props: TextProps) {
  const { render, ...otherProps } = props;

  const element = useRender({
    defaultTagName: 'p',
    render,
    props: mergeProps<'p'>({ className: styles.Text }, otherProps),
  });

  return element;
}
```

## Rules of render — the footguns ([#4039](https://github.com/mui/base-ui/issues/4039))

- **`render={<Component />}`: yes.** The element form is auto-merged and is what you want by default.
- **`render={Component}`: never.** Passing the bare component reference (not an element, not a callback) makes React treat each call as a new function identity; any hooks inside crash because this breaks the Rules of Hooks during reconciliation. We shipped a dev warning for this after [#4039](https://github.com/mui/base-ui/issues/4039).
- **No hooks inside render functions.** The function form (`render={(props, state) => ...}`) is called as a plain function on every render, not mounted as a component, so calling a hook inside it violates the Rules of Hooks for the same reason as the bullet above.
- **Forgetting to spread props** in the function form silently drops handlers/refs. The custom-component contract is to forward the `ref` and spread all the received props.
- **Polymorphism without a signal**: switching the rendered tag can leave invalid defaults (e.g. `type="button"` on an `<a>`). Our own `Button` solves this with a `nativeButton` prop; mirror that pattern rather than guessing.

## When to use

- Building your own design-system primitives that must accept `render` exactly like Base UI parts do.
- Migrating a Radix `Slot`-based component: our docs give a line-for-line equivalence.
- Merging an internal ref with the consumer's: the `ref` option accepts an array so both parties reach the underlying DOM element.

## When not to use

- **Consuming** a Base UI component: use its built-in `render` prop; `useRender` is only for authoring new render-prop hosts.
- **Merging props inside a render callback**: that's `mergeProps` alone, no hook needed.
- **Reading Base UI part state from outside**: use the `render`/`className` callback's `state` argument or controlled props; we rejected public context hooks for this ([#4329](https://github.com/mui/base-ui/issues/4329)).
